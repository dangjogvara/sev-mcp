# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A .NET 10 client for SEV's (Faroese electricity utility) customer REST API, intended to become an MCP server exposing meter and usage data. SEV's API reference PDF is SEV's document and isn't in the repo: keep a local copy at `docs/sev_rest_api_docs.pdf` (gitignored) and read it with `pdftotext -layout`. SEV's OpenAPI spec at https://github.com/dragan-norliga/sev-rest-clients/blob/master/DotNetExampleClient/api/openapi.yaml is more precise about field types and nullability; its example values (dates with `Z`/offsets, `application/json-patch+json`) are Swagger-generated and don't match the real API.

## Commands

```bash
dotnet build                                   # build the whole solution (SevMcp.slnx)
dotnet test                                    # run all tests (no network)
set -a; source .env; set +a; dotnet run --project Sev.SmokeTest   # run against the live API
dotnet user-secrets set "Sev:User" "..." --project Sev.McpServer  # one-time: credentials for the server
dotnet user-secrets set "Sev:Key" "..." --project Sev.McpServer
dotnet run --project Sev.McpServer --launch-profile http          # MCP server on http://localhost:5133/mcp
claude mcp add --transport http sev http://localhost:5133/mcp   # connect Claude Code to the local server
```

- `.env` (gitignored) holds `SEV_USER` and `SEV_KEY` for `Sev.SmokeTest`; nothing loads it automatically, so export it into the shell first. `Sev.SmokeTest` throws at startup if either is missing.
- `Sev.McpServer` reads credentials from the `Sev` configuration section (`SevOptions`): user-secrets locally (loaded only in the Development environment, which the launch profile sets), `Sev__User` / `Sev__Key` environment variables when hosted. It refuses to start if either is missing.
- Shared project settings (`TargetFramework`, `Nullable`, `ImplicitUsings`) live in `Directory.Build.props`, not in each `.csproj`.
- CI (`.github/workflows/ci.yml`) runs `dotnet restore`, `dotnet build` and `dotnet test`. Its `deploy` job then publishes `Sev.McpServer` to Azure App Service on pushes to `main` and manual runs (`gh workflow run ci.yml --ref main`). It runs only when the repository variable `AZURE_WEBAPP_NAME` is set, and logs in with GitHub OIDC through the `production` environment's secrets (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`).
- Hosting: `deploy/setup-azure.sh` (re-runnable, uses `az` and `gh`) creates the App Service (Linux B1, .NET 10, Always On, startup `dotnet Sev.McpServer.dll`), the Entra app registration Claude logs in with (v2 tokens, `mcp.access` scope, the MCP URL as an Application ID URI, Claude's callback), the app settings, and a deploy identity with a federated credential for the `production` environment. The credential's subject is read from GitHub (`/actions/oidc/customization/sub`): this repo uses immutable, ID-based subjects (`repo:<owner>@<id>/<repo>@<id>:...`), not `repo:<owner>/<repo>:...`. An existing resource group is reused wherever it is, and the plan is created in `LOCATION`, so a quota error can be fixed by running again in another region. The steps, connecting Claude and troubleshooting are in `docs/deploy-azure.md`. Don't run it or change Azure resources without the user's go-ahead: it creates billed resources.

## Architecture

- **Sev.Client**: class library with all API logic. `SevClient` wraps a caller-supplied `HttpClient` whose `BaseAddress` must be `SevClient.DefaultBaseAddress` (the constructor rejects a missing base address or one without the trailing `/`). Every public method takes an optional `CancellationToken`; pass it through from MCP tool handlers. `SevClient` doesn't log in itself: its `HttpClient` must include `SevAuthHandler`, which adds the Bearer token from `SevTokenProvider` to each request. `SevTokenProvider` logs in on first use with its own `HttpClient` (not through `SevAuthHandler`), logs in again 10 minutes before the 4-hour expiry, and must be a singleton so all requests share one token. On a 401, `SevAuthHandler` calls `SevTokenProvider.Invalidate`, logs in again and retries the request once (as a copy, since a request can only be sent once). `SevRateLimitHandler` refuses a request with `SevRateLimitExceededException` (with `RetryAfter`) when the shared singleton `SevRateLimiter` has seen 10 sent calls in the last 5 minutes. Every `HttpClient` that calls SEV, including the token provider's login client, must have it as the innermost handler (right before the network), so only requests actually sent are counted.
- **Caching** (`Sev.Client/SevCache.cs`, `SevDataService.cs`): `SevDataService` has the same methods as `SevClient` but serves from `SevCache` where possible. The meter list is kept for 6 hours; usage, cost and CO2 are kept per meter per day (`UsageDays`, `CostDays`, `Co2Days`), all through one generic `GetHourlyAsync<TReading>` (in steps: `MissingDays`, `FetchMissingAsync`, `Collect`) so the rules below are written once, only for days before today (Faroese time, via `SevTime`) with at least 23 readings, so days SEV hasn't finished delivering aren't frozen; days at least 7 days old (`SevCache.DaysUntilFinal`) are kept as SEV answered them, even with gaps or no readings, so outages aren't refetched on every call. Nothing from the current hour on is fetched (so a future range costs no call), and nothing outside a meter's install and removal dates, taken from the cached meter list (`get_usage` always loads it first; an unknown meter counts as installed). Missing data is fetched in pieces of at most 31 days (`MaxDaysPerRequest`), newest first, missing past days as whole days (`PiecesNewestFirst` groups only the missing days, so cached stretches longer than a piece are skipped, and each piece asks only for the meters missing in it), and at most 6 pieces per call (`MaxRequestsPerCall`); `UsageResult.NotFetched` reports the older part that didn't fit, and since fetched days are cached, asking again later completes it. A rate-limit refusal or empty answer after the first piece keeps what was fetched. Empty answers are never cached; when the first piece is empty, cached days are still returned, the rest is reported in `NotFetched`, and `UsageResult.EmptyAnswer` is set (likely throttling). `SevCache` is a singleton because it holds the data; `SevDataService` is transient because it holds a `SevClient`, whose `HttpClient` must stay short-lived.
- **Sev.McpServer**: the MCP server, using the Streamable HTTP transport (`ModelContextProtocol.AspNetCore`) at `/mcp`. `Program.cs` is a short overview; `SevServices.AddSevClient` registers `SevRateLimiter` and `SevTokenProvider` as singletons and `SevClient` as a typed `HttpClient` with `SevAuthHandler` then `SevRateLimitHandler`, and `SevCache` (singleton) with `SevDataService` (transient). Tools take `SevDataService`, never `SevClient` directly. Tools live in `Sev.McpServer/Tools/` and are registered with `WithTools<T>(toolJsonOptions)` (relaxed escaping keeps æ/ø/á readable). Only an `McpException`'s message reaches Claude (other exceptions become a generic error), so tools wrap SEV calls in `SevToolErrors.CallAsync` and throw `McpException` for invalid arguments. Keep tool logic in static methods so `Sev.McpServer.Tests` can test it without HTTP. Usage results must never present missing data as zero: `total` is `null` without readings, and `expectedHours` / `missingHours` / `note` show gaps (expected hours are the ended local hours in the range, from `HourlySummary.ExpectedHours`, limited to each meter's installation by `ExpectedHoursFor`: on the install and removal days the meter starts at its first reading and ends after its last one). `get_usage` (kWh), `get_cost` (SEV's estimated cost, unit `DKR`) and `get_co2` (SEV's estimated emissions, unit `Kg CO2`) share one implementation (`UsageTools.GetHourlySeriesAsync`) and aggregate the hourly data into hours, days or months in C# (`HourlySummary.Summarize`, which works on any `IMeterReadings` and returns `MeterSeriesResult`s), with the same `missingHours` per period, and marks periods SEV hasn't been asked for yet with `notFetched` plus a note telling Claude to ask again later. Any new aggregation must keep this. Real data shows why: one E350 meter delivers a day at a time, so today is always missing for it, while an E360 lags about an hour. Don't put real meter IDs, addresses or usage figures in the repo, issues or PRs: the repo is public. It is HTTP rather than stdio so it can later be hosted and used as a custom connector from the Claude web and mobile apps. Login depends on the `Auth` configuration section (`AuthOptions`, validated at startup). `McpLogin.AddLoginIfConfigured` reads it and `McpLogin.MapMcpEndpoint` maps `/mcp` for either mode. With `Auth:Authority` set (hosted), it adds JwtBearer (checks Entra ID v2 tokens: signature, issuer, `Audiences`, expiry; `MapInboundClaims = false` keeps `oid`), the SDK's `McpAuth` scheme as the challenge scheme (serves RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` with `resource` = `Auth:Resource`, which Claude requires to equal the MCP URL exactly, and answers 401 with `WWW-Authenticate: Bearer resource_metadata=...`), and the `AllowedUsers` policy on `MapMcp` (the token's `oid` must be in `Auth:AllowedUsers` and its `scp` claim must hold one of `Auth:Scopes`, compared by short name via `AuthOptions.ShortScopeName`, since the config has `api://<client-id>/mcp.access` and the token `mcp.access`; else 403). `X-Forwarded-Proto` is honoured so the challenge URL is https behind App Service. Without `Auth`, it only accepts local use: `AllowedHosts` (`appsettings.json`) allows only `localhost`, `127.0.0.1` and `[::1]`, and `LocalOrigin.UseLocalOriginsOnly` returns 403 for any `Origin` header that isn't a loopback origin, against DNS rebinding from a web page; requests without `Origin` (Claude Code) pass. Outside Development the server refuses to start without `Auth`. Hosted, `AllowedHosts` must be set to the host name. Claude's connectors (per Anthropic's docs) use a pre-registered client ("Use your own OAuth client"), redirect to `https://claude.ai/api/mcp/auth_callback`, and send the MCP URL as the RFC 8707 `resource`; with Entra that needs v2 tokens (`requestedAccessTokenVersion: 2`) and the MCP URL added as an Application ID URI. `Sev.McpServer.Tests/LoginTests.cs` starts the server with `WebApplicationFactory<Program>` and test-signed tokens.
- **Sev.Client.Tests**: xUnit tests for `SevClient`. `FakeHttpMessageHandler` returns canned responses and records requests, so tests never call the real API. `Fixtures/*.json` are sanitized copies of real API responses; keep their structure and field names exact when editing.
- **Sev.McpServer.Tests**: xUnit tests for the tools' pure logic (mapping, argument checks, error messages).
- **Sev.SmokeTest**: console app used as a manual smoke test: logs in, lists meters, prints hourly usage for all of the account's meters on a hardcoded date.

### JSON conventions
- `SevClient` serializes with `JsonNamingPolicy.SnakeCaseLower`, so models are PascalCase positional records that map to the API's snake_case fields. Use `[property: JsonPropertyName(...)]` only when the C# name differs from the API name (e.g. `UsageReading.Value` ← `reading`).
- `meter_id` is an `int` in `get_available_meters` but a `string` in usage responses; the models reflect this intentionally.
- The spec types `install_date`/`removal_date` as free-form nullable strings and `meter_nickname` as `object`. `Meter` reads them through the lenient converters in `Sev.Client/Json/`, so an unexpected value becomes `null` instead of failing the whole meter list.

## SEV API constraints

- **Rate limit: 10 calls per 5 minutes per customer**, login included. Reuse tokens and cache the meter list rather than calling per request. `SevRateLimiter` enforces it locally; it only sees this process's calls, so a server restart resets its count and other clients on the same account (the smoke test, scripts) aren't counted.
- `login_and_get_jwt_token` returns the JWT as `text/plain` (no JSON quotes, no trailing newline).
- JWTs expire after 4 hours; `refresh_jwt_key_token` (POST, no body, current Bearer token) returns a new plain-text one, but only while the current token is still valid. It is deliberately not used: it costs a rate-limited call just like a login, and login works whether or not the token has expired.
- All endpoints are POST. Date ranges are `[from_date, to_date)` and always in local Faroese time (send `DateTime` with `Kind` unspecified, no `Z`). `SevClient` throws `ArgumentException` for any other `Kind` or when `from >= to`, so convert at the boundary, not inside the client. The tools do this with `FaroeseTime.TryParse`, and the cache finds "today" with `SevTime`; both use `SevTime.Zone` (`Atlantic/Faroe`), which needs the system time-zone database: it's present on normal hosts, but slim Docker images need `tzdata` installed.
- `estimated_cost` (`SevClient.GetEstimatedCostAsync`) takes the same request as `hourly_kwh_usage` and returns one reading per hour (observed 2026-11-21): `reading` is the hour's cost, `unit` is `"DKR"`, `price_unit` the price per kWh, `tarif` the installation's tariff number; no `cumulative_value`. Hourly readings implement `IHourlyReading`, so new hourly series can reuse the caching and summarizing.
- `estimated_CO2` (`SevClient.GetEstimatedCo2Async`) takes the same request as `hourly_kwh_usage` and returns one reading per hour (observed 2026-11-22): `reading` in kg CO2, `unit` `"Kg CO2"`, `cumulative_value` always `null` (so `Co2Reading` leaves it out). SEV computes each hour as (1 − green share of production that hour) × kWh × 0.641 kg CO2/kWh.
- **`hourly_kwh_usage` returns at most 31 days per call and silently drops the rest** (observed 2026-11-21: a request for 2025-11-21 to 2026-11-21 returned 2025-11-21 to 2025-12-21 only). `SevDataService` splits longer ranges; a year therefore takes 12 calls, more than one rate-limit window.
- **Over the rate limit, SEV returns `200 OK` with an empty list**, not an error (observed 2026-11-21: `get_available_meters` returned `[]` after ~11 calls in a few minutes, and the meters again after waiting 5 minutes; the docs don't mention it). So an empty result usually means throttling: the tools report it via `SevToolErrors.ThrowIfEmpty` (meter list) and `ThrowIfEmptyAnswer` (usage, only when there are no cached readings to show either). Don't trigger it on purpose, and keep manual testing to a few calls at a time.
- Responses are standard HTTP status codes. On a non-success status `SevClient` throws `SevApiException` (derives from `HttpRequestException`) with `StatusCode`, `ResponseBody` and `RetryAfter`.

## Workflow

Every change, including docs, goes through an issue and a PR. Never commit directly to `main`.

1. `gh issue create` first.
2. Branch from an up-to-date `main` as `feature/<issue#>-<slug>` (e.g. `feature/9-docs-and-claude-md`).
3. Open the PR with `Closes #<issue#>` in the body.
4. Only merge when asked: wait for CI to pass, then `gh pr merge <pr#> --squash --delete-branch`.

Never rename the head branch of an open PR. GitHub closes the PR instead of retargeting it.
